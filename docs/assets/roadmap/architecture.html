Snapshot 19 Oct 2026

Architecture

What we are building
ROS 2 Jazzy software on a Jetson (Nav2, MoveIt 2, ros2_control for the arms), a micro-ROS base controller, and a hardwired safety chain under everything.
Where we are
Nav2 output passes through the smoother and collision monitor; reactive stopping has not been demonstrated (S2). Four other motion sources bypass them. The 2.0 base firmware and the combined upper-body model are not on main.
What is next
One arbitrated command path (twist_mux ahead of the smoother), a reactive layer that is never switched off and has its own lifecycle, a latched software stop and base command timeouts, before rc.1.

Critical gaps before rc.1

Critical: Commands held at zero across E-stop and RESET (AR-05)

After RESET, the last non-zero command from a direct source reaches the base (inferred from S6 and S7 plus no consumer on main).

Closure test: After RESET, no motion from any source until an explicit operator release; verified in simulation and on the bench.

Planned chain

twist_mux > velocity_smoother > collision_monitor (stop, slowdown and approach polygons; LiDAR plus near-field sources) > /cmd_vel > base (controller watchdog; simulated base with cmd_vel timeout)

Reactive motion layer (velocity_smoother and collision_monitor) under its own lifecycle manager with respawn; the arbiter outputs zero when the monitor is inactive. Base command timeout: firmware watchdog (Gate A 200 ms) and diff_drive_controller cmd_vel_timeout in simulation. Software stop: stop_lock at priority 255, latched until released.

Below all software: the hardwired E-01 chain (two E-stops, PNOZ s3, K1/K2). Software stops are functional stops only.

Names and priorities are proposals from the #35 branch and audit pass 2; they change only through a contract change request.

AR-01 Command arbitration critical before rc.1
What we do
Only Nav2 output passes the smoother and collision monitor; reactive stopping has not been demonstrated (S2). The UI, docking, a UI-launched controller and replay publish the final /cmd_vel.
Good practice
Every source enters a multiplexer with priorities, per-input timeouts and lock topics, ahead of the smoother and the collision monitor (twist_mux pattern used by common ROS 2 platforms).
Gap
Four bypasses observed at runtime (S3, S4, S5).
Recommendation
Land #35 with twist_mux ahead of velocity_smoother; move the UI to a teleop input with a deadman; remove UI-launched navigation; restrict replay. Add one launch test per source that asserts collision_monitor is the only /cmd_vel publisher.

AR-02 Reactive layer never switched off critical before rc.1
What we do
Docking deactivates collision_monitor through its lifecycle service for the final approach.
Good practice
The collision monitor stays active; docking-specific behaviour uses polygons (stop, slowdown, approach) or a reduced-speed zone, and the docking controller runs through the same chain.
Gap
No reactive layer during docking; the lifecycle manager resets the stack; status misreports the monitor.
Recommendation
Remove the lifecycle calls (#35 option b). Evaluate the DockStop polygon; until decided, cap docking speed and keep the monitor active.

AR-05 Commands held at zero across E-stop and RESET critical before rc.1 new in this review
What we do
No host node consumes the safety-relay state; sources keep publishing while actuator power is off.
Good practice
When actuator power is removed, the command path locks and requires a fresh zero then an explicit new command after RESET.
Gap
After RESET, the last non-zero command from a direct source reaches the base (inferred from S6 and S7 plus no consumer on main).
Recommendation
Publish the Y32 state from the base controller (diagnostic) and engage the stop lock while it is low; owners implement, and it is not a safety function.

After RESET, no motion from any source until an explicit operator release; verified in simulation and on the bench.

New in this review: findings with code evidence

NR-01: The final velocity command is an unstamped Twist on every path should-fix confidence: verified new in this review

Nav2 is configured without stamped velocity commands and the UI publishes geometry_msgs/Twist. A consumer of /cmd_vel cannot reject a stale or reordered command by its age; only the base watchdog bounds it. Nav2 Jazzy supports TwistStamped on the whole chain (enable_stamped_cmd_vel).

Evidence: nav2_params.yaml on main has no enable_stamped_cmd_vel; live graph in pass 2 shows geometry_msgs/msg/Twist on /cmd_vel, /cmd_vel_nav and /cmd_vel_smoothed.

Code: openamr-platform-sw/ros2/src/openamrobot_nav2/config/nav2_params.yaml

Priority: before v2.0.0 · owner @skunal3318 (navigation lead)

NR-02: No SROS2 configuration found in the inspected repositories should-fix confidence: verified new in this review

No SROS2 configuration was found in the inspected repositories (launch files, configuration and documents on main of every product repository). Whether DDS security is required depends on the deployment network; no qualified assessment has decided it. Area-level gap; it does not replace the UI command path hardening work.

Evidence: Search of launch, YAML and package files on main of every product repository for SROS2 settings returned no configuration hit.

Priority: before v2.0.0 · owner @parthkeshari (UI lead)

NR-03: Motion sources keep publishing while actuator power is off; nothing holds them at zero across a RESET blocker confidence: inferred new in this review

The host has no consumer of the safety-relay state (Y32 or /estop). Navigation, docking and UI sources continue to publish while the E-stop has removed actuator power. After a deliberate RESET the last non-zero command from any direct source reaches the base. P-03 item 20 requires that motion still needs a command after RESET; today a stale command satisfies that.

Evidence: No subscriber to an E-stop or safety-relay state topic on main; S7a shows a direct source keeps its last command; the UI stop does not latch (S6).

Priority: critical before rc.1 · owner @skunal3318 (navigation lead)

NR-04: Package names mix two prefixes and one name exists twice later confidence: verified new in this review

Packages use openamr_ and openamrobot_ prefixes, and openamr_ui_msgs exists in two repositories. REP 144 asks for unique, consistent package names.

Evidence: package.xml files on main (see the package graph on this page).

Priority: later · owner to be confirmed

NR-05: No risk assessment found in the inspected repositories should-fix confidence: opinion new in this review

No risk assessment was found in the inspected repositories. The LiDAR, ToF and ultrasonic sensors are functional sensing only, and the hardwired safety function is the two E-stops. Standards such as ISO 3691-4 describe personnel detection set from a risk assessment, or operating-zone restrictions; no qualified assessment has established which standards apply to this robot and deployment.

Evidence: decisions.yaml NAV-LIDAR and TELEMETRY-NOT-SAFETY-EVIDENCE; P-03 item 13 (functional sensing only); no risk assessment file in any repository.
